# 响应速度优化与验证

本次针对可复现的重复工作优化，没有使用跨请求权限缓存，也没有用静态假数据替代实时业务数据。

| 位置 | 优化前 | 优化后 |
| --- | --- | --- |
| 工作概览 | 班次、授课、任务各请求两遍，共6次，并渲染两遍 | 各请求一次，共3次，统一渲染 |
| 编辑表单 | 下拉选项接口逐个等待 | 不同选项接口并行请求，同类型只请求一次 |
| 模板列表 | 每个模板重复查询两次维度，共1+2N次SQL | 模板和全部维度分别批量读取，共2次SQL |
| 报表答卷维度 | 每份答卷单独一次SQL | 一个任务的答卷维度统一一次SQL，再按答卷组装 |
| 业务账号信息 | 同一请求中权限、范围、审计反复查询 | 同一请求内复用一次，下一请求重新查询 |
| CSS、JS子资源 | 已登录时也逐个查询账号状态 | 公开静态资源跳过账号查询，API仍逐次校验 |
| 后台写请求 | 每次额外等待一次CSRF接口 | 同一会话复用令牌，登录、退出、改密、401/403后清除 |
| 任务按钮整理 | 每行重新扫描整张表查找行号 | 单次遍历直接取当前行号 |

前端冒烟测试记录实际发出的请求，断言概览只有3次数据请求、同会话CSRF复用及登出后重新获取。后端集成测试覆盖账号停用、改密、撤权、班次范围、报表内容以及评价提交，避免优化损坏权限和数据一致性。

这里的请求和SQL数量是代码路径与测试可验证的结果，不代表网络耗时降低相同比例。实际响应时间还受数据库、运行机器和访问链路影响。可在浏览器开发者工具 Network 中比较本机访问与隧道访问的接口 Waiting/TTFB，区别服务器处理耗时和公网链路延迟。

列表仍采用现有接口返回数据后分页的方式；若后续人员、课程达到数万条，应进一步改成服务端分页与检索。本轮没有通过长期缓存业务列表掩盖这一规模边界。
